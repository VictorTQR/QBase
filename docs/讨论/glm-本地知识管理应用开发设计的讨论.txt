### 🧩 推荐方案：插件化架构 + 标准接口
这是最能满足您复杂需求、且具备良好扩展性的方案。您可以像搭积木一样，根据知识管理的具体任务动态加载不同的功能模块。
#### 1. 设计原则
*   **核心轻量**：知识管理应用本身（“核心”）只负责最核心的**知识组织、关联、存储和展示**逻辑。它像一个“操作系统”，负责调度。
*   **接口统一**：为转录、TTS、文档解析等模块定义清晰的**接口（Interface）**。核心通过这些接口与模块交互，而不关心具体实现。
*   **插件形式**：将各个功能模块开发成**独立的插件或动态库**。核心在需要时动态加载它们。
*   **独立可用**：每个插件（模块）都应能以**命令行工具、独立窗口或Web服务**的形式单独启动和运行，满足您单独使用的需求。
#### 2. 架构示例
```

├── 插件系统

│   ├── TTS插件

├── 核心功能

    ├── 管理器窗口（全局设置）
    └── 独立模块窗口（可由核心或单独启动）
```
#### 3. 技术实现要点
为了实现上述架构，您可以考虑：
*   **接口定义**：使用语言特性（如 Go 的 interface、Python 的抽象基类）或简单的协议（如定义JSON-RPC或REST API）来规范模块的输入输出。
    > 💡 **例如**：为“转录模块”定义一个 `Transcribe(audioPath string) (text string, err error)` 的接口，核心调用时无需知道背后是调用了哪个云服务API还是本地Whisper模型。
*   **进程间通信（IPC）**：当模块以独立进程运行时，核心可通过IPC（如本地TCP端口、Unix Domain Socket、消息队列）调用模块。这使模块完全解耦，甚至可以用不同语言开发。
*   **动态加载**：如果希望核心启动更快、资源占用更低，可采用进程内插件机制，核心在需要时通过动态库加载插件（需注意版本和依赖管理）。
*   **配置中心**：一个统一的配置文件或数据库，管理各模块的参数（如API密钥、模型路径），核心和模块都可以访问。

*   **功能模块**：作为**插件**存在，核心通过标准接口调用。同时，每个插件都拥有一个“独立入口”（如 `--standalone` 参数或单独的可执行文件），满足您单独使用的需求。

import subprocess
import json
def call_transcribe_cli(audio_path: str) -> str:
    """调用转录CLI工具"""
    cmd = ["python3", "transcribe_cli.py", "transcribe", audio_path, "--output=json"]
    
    try:
        # 启动子进程，捕获输出
        result = subprocess.run(
            cmd, 
            capture_output=True, 
            text=True, 
            check=True
        )
        # 解析JSON输出
        response = json.loads(result.stdout)
        return response.get("result", "")
        
    except subprocess.CalledProcessError as e:
        # 处理错误
        print(f"CLI调用失败: {e}")
        return ""
# 在核心业务中使用

import subprocess
import json
from pathlib import Path
class ModuleRunner:
    def __init__(self):
        # 加载配置
        with open("config.json", "r") as f:
            config = json.load(f)
        self.python_exe = config["module_python_path"]
        self.cli_root = config["transcribe_cli_path"]
    def run_transcribe(self, audio_path):
        """在独立的虚拟环境中运行 CLI"""
        cmd = [
            self.python_exe,  # 关键：使用模块专用的 Python 解释器
            self.cli_root,
            "transcribe",
            audio_path,
            "--output", "json"
        ]
        
        # 运行子进程
        result = subprocess.run(cmd, capture_output=True, text=True)
        
        if result.returncode != 0:
            print(f"Error: {result.stderr}")
            return None
        
        return result.stdout
# 使用

### 2.2 关键技术选型
*   **界面层**：DearPyGui（高性能，适合展示列表和文本）。
*   **存储层**：LanceDB（嵌入式向量数据库，无需额外服务进程）。
*   **通信层**：`subprocess` + JSON-RPC（主应用通过标准输入输出调用 CLI，实现环境隔离）。
*   **AI 层**：OpenAI Compatible API（支持本地 Ollama 或云端 API）。
## 3. 功能需求
### 3.1 知识库初始化与管理
*   **新建/打开知识库**：用户选择一个本地文件夹作为知识库根目录。
*   **元数据存储**：在根目录下创建 `.kb_meta/` 隐藏文件夹，存储 `config.json` 和 `lancedb/` 数据。
*   **配置管理**：用户可在界面配置 OpenAI API Base URL 和 API Key。
### 3.2 文件扫描与索引
*   **启动扫描**：应用启动时，递归扫描根目录，识别支持的文件类型（mp3, mp4, pdf）。
*   **状态同步**：
    1.  检测是否存在附属文件（如 `video.transcript.txt`），若有则入库。
    2.  若无，标记为“待处理”。
*   **手动刷新**：提供“扫描变更”按钮，用于处理外部手动添加文件的情况。
### 3.3 内容解析与转录
*   **触发方式**：用户在界面右键菜单选择“生成转录”或“解析 PDF”。
*   **进程调用**：
    *   主应用从配置中读取模块专用 Python 解释器路径。
    *   启动子进程运行 CLI，并显示进度条（如果 CLI 支持）。
*   **产物落地**：CLI 必须在源文件同目录生成符合命名规范的产物文件。
    *   命名规范：`<filename>.<type>.txt` 或 `<filename>.<type>.md`。
### 3.4 向量化与 AI 增强
*   **向量化**：
    *   当检测到新的文本类产物（.txt/.md）时，自动触发 Embedding 流程。
    *   支持配置本地 Embedding 模型（如 BGE）或云端 API。
    *   向量存入 `.kb_meta/lancedb`。
*   **生成总结**：
    *   用户点击“生成总结”。
    *   应用读取文本内容，调用 LLM API（System Prompt 预设），生成分页或分段总结。
    *   结果保存为 `<filename>.summary.md`。
### 3.5 搜索与交互
*   **三种搜索模式**：
    1.  **文件名搜索**：模糊匹配文件名。
    2.  **全文搜索**：基于 LanceDB 的 FTS 能力或 Python `whoosh` 库（可选）。
    3.  **语义搜索**：输入自然语言查询，计算 Query 向量，在 LanceDB 中检索 Top-K。
*   **文件查看**：
    *   双击文件调用系统默认应用打开（如 VLC, Acrobat）。
    *   界面内提供侧边栏，展示相关的 `.txt` 和 `.md` 内容。
## 4. 数据定义
### 4.1 文件命名约定
所有中间产物与源文件同级存放，遵循点号分隔规范：
| 产物类型 | 文件名示例 | 说明 |
| :--- | :--- | :--- |
| **源文件** | `interview.mp4` | 用户原始文件 |
| **转录文本** | `interview.transcript.txt` | 转录 CLI 生成 |
| **PDF 解析文本** | `report.parse.txt` | PDF 解析 CLI 生成 |
| **AI 总结** | `interview.summary.md` | 主应用生成 |
| **向量缓存** | (存入数据库) | 不生成单独文件 |
### 4.2 LanceDB 表结构
表名：`knowledge_vectors`
| 字段名 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | String | UUID |
| `file_path` | String | 源文件绝对路径 |
| `content` | String | 文本片段内容 |
| `vector` | Vector(1536) | Embedding 向量 |
| `metadata` | JSON | 包含 type, create_time 等 |
## 5. 界面设计草案
*基于 DearPyGui 布局描述：*
*   **左侧导航栏**：
    *   知识库列表/目录树。
    *   状态统计（已索引文件数、待处理数）。
*   **中间主区域**：
    *   文件列表表格（列：文件名、类型、大小、状态[已索引/未处理]、创建时间）。
    *   右键菜单：打开、转录、生成总结、重新索引、删除。
*   **右侧详情面板**：
    *   文件基本信息。
    *   Tab 页签：[预览文本] [AI 总结] [元数据]。
    *   底部：快捷操作按钮。
*   **顶部工具栏**：
    *   搜索框（下拉选择：语义/关键字）。
    *   设置按钮（API配置）。
