## 一、总体结论

你的知识管理应用应该主要负责：

1. 知识资产管理

2. 元数据管理

3. 搜索与索引

```text
      ├── 摘要模块
      └── 向量索引模块
```

## 二、你真正要区分的是四层

很多自用工具一开始混乱，是因为把下面几层混在一起了。

### 1. 能力层

这是“做事”的模块。

例如：

- 文档解析：PDF、Word、Markdown、HTML、图片 OCR。
- 转录：音频转文字。
- TTS：文字转语音。
- 摘要：调用 LLM 或本地模型生成摘要。
- 分块：把长文档切成适合检索的片段。
- Embedding：生成向量。

这些模块应该是可复用的。

它们不应该知道自己是在给“知识管理应用”服务，还是单独被命令行调用。

---

### 2. 接口层

能力模块要暴露统一、稳定的调用方式。

常见形式有三种：

#### 方式一：函数库

适合轻量模块。

例如 Python：

```python
from mytools.parsing import parse_document
from mytools.asr import transcribe_audio
from mytools.tts import synthesize_speech

result = parse_document("input.pdf")
text = transcribe_audio("meeting.m4a")
audio = synthesize_speech("你好，世界")
```

优点：

- 最简单。
- 没有网络开销。
- 调试方便。

缺点：

- 如果模型很重，每次调用都要加载。
- 多个应用同时使用可能不方便。

---

#### 方式二：CLI 命令

适合你平时也会单独使用这些功能。

例如：

```bash
mytool parse input.pdf -o output.md
mytool transcribe meeting.m4a -o result.json
mytool tts "你好" --voice zh-CN -o output.wav
```

优点：

- 非常适合自用。
- 可以被知识管理应用调用。
- 可以独立调试。
- 可以写进脚本、快捷指令、Raycast、Alfred、Shell 别名等。

缺点：

- 每次调用可能重新启动进程。
- 大模型加载可能慢。

---

#### 方式三：本地服务

适合重模块，比如：

- Whisper 转录。
- 本地 TTS。
- OCR。
- Embedding 模型。
- 本地 LLM。

例如：

```text
http://127.0.0.1:8787/parse
http://127.0.0.1:8787/transcribe
http://127.0.0.1:8787/tts
```

或者本地 WebSocket、gRPC、Unix Socket、Named Pipe。

优点：

- 模型常驻内存或 GPU。
- 响应快。
- 多个客户端可以共用。
- 可以做任务队列和进度通知。

缺点：

- 复杂度更高。
- 需要管理进程启动、端口、日志、崩溃恢复。

---

### 3. 数据层

知识管理应用最重要的是数据层。

你需要保存的不是“调用了一次功能”，而是“这次调用产生了什么资产”。

例如一次转录任务，应该记录：

```json
{
  "task_id": "task_20260816_001",
  "type": "transcription",
  "source_file": "meetings/2026-08-16.m4a",
  "source_hash": "sha256:xxxx",
  "status": "success",
  "created_at": "2026-08-16T10:20:00+08:00",
  "model": "whisper-large-v3",
  "language": "zh",
  "duration": 3520,
  "output_text": "assets/transcripts/task_20260816_001.txt",
  "output_segments": "assets/transcripts/task_20260816_001.segments.json",
  "error": null
}
```

一次文档解析任务，应该记录：

```json
{
  "task_id": "task_20260816_002",
  "type": "document_parsing",
  "source_file": "papers/attention.pdf",
  "status": "success",
  "parser": "marker",
  "output_markdown": "assets/parsed/attention.md",
  "output_meta": "assets/parsed/attention.meta.json",
  "page_count": 15,
  "has_ocr": false
}
```

这样你的知识管理应用才不会只是一个“调用器”，而是真正的“知识资产中心”。

---

### 4. 展示层

也就是你日常使用的界面。

可以是：

- Web 页面。
- Tauri 桌面应用。
- Electron 桌面应用。
- Obsidian 插件。
- VS Code 插件。
- 命令行 TUI。
- 本地 FastAPI + 浏览器页面。

自用项目建议不要一开始做太重的界面，先保证数据结构和任务流程稳定。

## 四、关键设计：能力模块要输出标准结果

你以后会越来越多地复用这些模块，所以一开始就要约定输出格式。

不要每个模块随便返回一个字符串。

建议统一成类似这样：

```json
{
  "status": "success",
  "module": "transcription",
  "version": "0.3.1",
  "model": "whisper-large-v3",
  "input": {
    "path": "/data/audio/meeting.m4a",
    "hash": "sha256:xxxx"
  },
  "outputs": {
    "text": "/data/results/meeting.txt",
    "segments": "/data/results/meeting.segments.json"
  },
  "meta": {
    "language": "zh",
    "duration_seconds": 3520
  },
  "logs": [],
  "error": null
}
```

这样知识管理应用只需要理解一种标准结果。

例如：

```python
result = run_tool(
    tool="transcription",
    input_path="audio/meeting.m4a",
    options={
        "language": "zh",
        "model": "large-v3"
    }
)
```

然后知识管理应用把 `result` 存入数据库。

## 五、什么时候适合直接集成代码？

如果满足下面条件，可以直接作为函数库集成到知识管理应用中：

1. 模块很轻。
2. 没有复杂依赖。
3. 不需要常驻模型。
4. 不需要被多个应用同时调用。
5. 你只想快速完成功能。
6. 调用频率不高。

例如：

- Markdown 清洗。
- 文件名规范化。
- 简单 HTML 转 Markdown。
- 文本分块。
- 本地文件哈希。
- 简单正则提取。
- 元数据读取。

这些可以直接放进核心应用或公共包里。

## 六、什么时候适合做成 CLI？

如果满足下面条件，建议做成 CLI：

1. 你平时会单独使用。
2. 可能被脚本调用。
3. 可能被知识管理应用调用。
4. 模块逻辑比较独立。
5. 不需要长期常驻。
6. 不想引入服务进程。

例如：

```bash
kb parse document.pdf
kb transcribe meeting.m4a
kb tts "今天需要整理三篇论文"
kb summarize note.md
```

对于自用系统，CLI 是非常好的中间形态。

它既简单，又保留了独立性。

知识管理应用可以通过子进程调用：

```python
subprocess.run([
    "mytool",
    "transcribe",
    "meeting.m4a",
    "--output",
    "result.json"
])
```

然后读取 JSON 结果。

## 七、什么时候适合做成本地服务？

如果满足下面条件，再考虑本地服务：

1. 模型加载很慢。
2. 需要 GPU。
3. 多个应用需要同时调用。
4. 需要任务队列。
5. 需要实时进度。
6. 需要流式输出。
7. 模块使用频率很高。
8. 你希望知识管理应用只发请求，不管理模型生命周期。

典型例子：

- Whisper 转录服务。
- 本地 TTS 服务。
- OCR 服务。
- Embedding 服务。
- 本地 LLM 服务。
- RAG 检索服务。

例如：

```text
POST /transcribe
{
  "audio_path": "/data/audio/meeting.m4a",
  "language": "zh"
}
```

返回：

```json
{
  "task_id": "abc123",
  "status": "processing"
}
```

然后知识管理应用轮询：

```text
GET /tasks/abc123
```

或者通过 WebSocket 接收进度。

## 八、不要一开始就过度微服务

自用项目最常见的错误是：

> 明明只是本地工具，却一开始拆成五六个服务，每个服务都有独立数据库、独立配置、独立部署流程。

这会带来很多麻烦：

- 端口冲突。
- 服务没启动。
- 路径不一致。
- 日志分散。
- 版本不兼容。
- 配置混乱。
- 数据难以追踪。

所以建议你按这个顺序演进：

```text
脚本
↓
函数库
↓
CLI
↓
本地服务
↓
插件化平台
```

不要一开始直接跳到最后一步。

## 十一、知识管理应用里要有一个 Adapter 层

不要让知识管理核心代码直接依赖某个具体实现。

例如不要这样：

```python
from whisper import transcribe
from some_pdf_lib import extract_text
from tts_engine import speak
```

而是这样：

```python
class TranscriptionAdapter:
    def run(self, task):
        raise NotImplementedError
```

然后具体实现可以是：

```python
class WhisperCliAdapter(TranscriptionAdapter):
    def run(self, task):
        # 调用 whisper CLI
        ...

class WhisperServerAdapter(TranscriptionAdapter):
    def run(self, task):
        # 调用本地 HTTP 服务
        ...

class CloudAsrAdapter(TranscriptionAdapter):
    def run(self, task):
        # 调用云端 ASR
        ...
```

这样你以后可以随意替换：

- 本地 Whisper。
- Faster-Whisper。
- mlx-whisper。
- 云端 ASR。
- 其他 TTS 引擎。
- 不同 PDF 解析器。

知识管理核心不用改。

## 十八、如何决定某个模块是“集成”还是“独立”？

可以用下面这个判断表。

| 问题 | 是 | 否 |
|---|---|---|
| 这个模块是否经常单独使用？ | 独立 CLI/包 | 可以集成 |
| 是否有重模型或 GPU？ | 服务化 | 可集成 |
| 是否多个应用都要调用？ | 服务化或公共包 | 可集成 |
| 是否启动慢？ | 服务化 | 可集成 |
| 是否需要实时进度？ | 服务化或任务系统 | 简单调用即可 |
| 是否依赖很多特殊库？ | 独立模块 | 可集成 |
| 是否更新频繁？ | 独立模块 | 可集成 |
| 是否只是简单文本处理？ | 可集成 | 独立意义不大 |

# 一、推荐总体思路

你的主应用不要把自己当成“文件唯一生产者”，而应该当成：

```text
文件库观察者 + 索引器 + 任务调度器 + 查看器
```

核心原则：

1. **原始文件不动**
   - 播客音频、视频、文档仍然按你现有目录结构存放。
   - 主应用不强制移动、改名、转换格式。

2. **派生文件按约定识别**
   - 转录文本：`.txt` / `.transcript.txt` / `.transcript.json`
   - AI 总结：`.summary.md`
   - 笔记：`.notes.md`
   - 文档解析结果：`.parsed.md`
   - 元数据：`.meta.json`

3. **隐藏目录存应用数据**
   - 在你选定的库根目录下创建 `.knowledge/` 或 `.kb/`。
   - 里面放 SQLite、向量索引、任务记录、缓存、配置。

4. **主应用触发和手动 CLI 都只产生文件**
   - 主应用触发转录：调用 CLI，然后扫描结果。
   - 手动 CLI：生成文件后，主应用通过扫描或监听发现结果。

5. **数据库只是缓存和索引**
   - 删除 `.knowledge/` 后，应该可以重新扫描目录并恢复大部分管理能力。
   - 这样系统会很稳，也不会被数据库绑死。

# 三、派生文件应该如何存放？

你有两个主要选择。

---

## 方案 A：同目录同名 sidecar 文件

这是你目前转录 CLI 的方式。

例如：

```text
podcasts/
├── episode-001.mp3
├── episode-001.txt
├── episode-001.summary.md
└── episode-001.notes.md
```

识别规则可以是：

```text
episode-001.mp3          原始音频
episode-001.txt          转录文本
episode-001.summary.md   AI 总结
episode-001.notes.md     用户笔记
episode-001.meta.json    元数据，可选
```

优点：

- 简单直观。
- 兼容你现在的 CLI。
- 在文件管理器里很容易看到。
- 手动 CLI 生成后非常自然。

缺点：

- 文件多了以后目录会比较乱。
- 一个原始文件可能有多个派生文件，命名规则要越来越严格。
- 多个模型、多个版本的转录结果不好放。

如果采用这个方案，建议后续把命名稍微规范化：

```text
episode-001.mp3
episode-001.transcript.txt
episode-001.transcript.json
episode-001.summary.md
episode-001.notes.md
episode-001.meta.json
```

但为了兼容现有 CLI，可以同时识别：

```text
episode-001.txt
episode-001.transcript.txt
```

---

## 方案 B：每个原始文件一个隐藏 sidecar 文件夹

例如：

```text
podcasts/
├── episode-001.mp3
└── episode-001.mp3.kb/
    ├── transcript.txt
    ├── transcript.json
    ├── summary.md
    ├── notes.md
    └── meta.json
```

或者：

```text
episode-001.mp3
episode-001.kb/
```

优点：

- 派生文件集中管理。
- 目录更干净。
- 容易放多版本结果。
- 不容易和普通文件混淆。
- 删除原始文件时可以连同 `.kb/` 一起删除。

缺点：

- 你现有 CLI 默认输出同名 `.txt`，需要适配或迁移。
- 某些文件管理器默认不显示隐藏目录。
- 手动查看派生文件稍微多一步。

---

## 我的建议

短期：

> 兼容你现在的 CLI，使用同目录同名文件。

长期：

> 逐步迁移到每个资产一个 `.kb/` sidecar 目录，或者至少支持这种模式。

最稳的方式是主应用同时支持两种：

```text
如果存在 episode-001.mp3.kb/transcript.txt，则优先使用它；
否则尝试使用 episode-001.txt；
否则尝试使用 episode-001.transcript.txt。
```

这样既不破坏你现在的 CLI，也能逐渐演进。

# 四、主应用和 CLI 的关系

你可以把主应用和 CLI 的关系设计成这样：

```text
主应用
  ├── 扫描文件库
  ├── 建立资产记录
  ├── 建立搜索索引
  ├── 显示文件详情
  ├── 创建任务
  ├── 调用 CLI
  ├── 监听/扫描 CLI 输出
```

CLI 不需要知道主应用是否存在。

主应用也不需要假设所有文件都是自己生成的。

这样你可以：

```bash
mytool transcribe podcasts/episode-001.mp3
```

然后主应用扫描到：

```text
podcasts/episode-001.txt
```

自动识别为：

```text
episode-001.mp3 的转录文本
```

并加入索引。

# 五、核心概念：Asset 和 Artifact

建议你在主应用内部明确区分两个概念。

---

## Asset：原始知识资产

例如：

```text
podcasts/episode-001.mp3
videos/talk-001.mp4
documents/paper.pdf
```

Asset 是被管理的主体。

字段可以包括：

```text
asset_id
title
type: audio / video / document
path
relative_path
file_hash
size
mtime
created_at
updated_at
status
```

---

## Artifact：派生产物

例如：

```text
episode-001.txt
episode-001.summary.md
episode-001.notes.md
paper.parsed.md
talk-001.transcript.json
```

Artifact 是围绕 Asset 产生的文件。

字段可以包括：

```text
artifact_id
asset_id
kind: transcript / summary / note / parsed / meta / embedding_cache
path
relative_path
file_hash
mtime
source: app / cli / external
generator: whisper / llm / user
model
created_at
```

例如：

```text
Asset:
  path = podcasts/episode-001.mp3
  type = audio

Artifact 1:
  kind = transcript
  path = podcasts/episode-001.txt

Artifact 2:
  kind = summary
  path = podcasts/episode-001.summary.md

Artifact 3:
  kind = note
  path = podcasts/episode-001.notes.md
```

这样无论谁生成了 `episode-001.txt`，主应用都知道它是某个 Asset 的 transcript。

# 七、如何同时支持主应用触发和手动 CLI？

关键在于：

任务记录只是辅助。

---

## 场景 1：主应用触发转录

流程：

```text
1. 用户选中 episode-001.mp3
2. 点击“生成转录”

4. 主应用调用 CLI：
   mytool transcribe podcasts/episode-001.mp3

6. 主应用检测到文件生成
7. 主应用导入 artifact
8. 主应用更新全文索引和向量索引
9. 任务标记成功
```

数据库里可以有：

```text
Task:
  task_id = task_001
  asset_id = asset_episode_001
  type = transcription
  source = app
  status = success
  output = podcasts/episode-001.txt
```

## 场景 2：你手动运行 CLI

流程：

```text
1. 你在终端运行：
   mytool transcribe podcasts/episode-001.mp3
2. CLI 生成 podcasts/episode-001.txt
3. 主应用通过文件监听或定期扫描发现新文件
4. 主应用识别它是 episode-001.mp3 的 transcript
5. 主应用导入 artifact
6. 主应用更新索引
```

数据库里可以有：

```text
Artifact:
  artifact_id = artifact_002
  asset_id = asset_episode_001
  kind = transcript
  path = podcasts/episode-001.txt
  source = external_cli
```

即使没有 Task，也没关系。

# 八、主应用如何发现外部 CLI 生成的文件？

有三种方式，可以组合使用。

---

## 1. 启动时全量扫描

主应用启动时扫描整个库：

```text
遍历所有文件
  ├── 识别原始文件
  ├── 识别派生文件
  ├── 对比数据库
  ├── 新增缺失记录
  ├── 更新变化文件
  └── 删除已不存在记录
```

优点：

- 最稳。
- 不依赖监听。
- 可以恢复数据库损坏或漏掉的文件。

缺点：

- 大库首次扫描较慢。

建议一定要有这个功能。

---

## 2. 文件监听

使用文件系统监听：

```text
新建文件
修改文件
删除文件
重命名文件
```

常见库：

- Python：`watchdog`
- Node.js：`chokidar`
- Rust/Tauri：`notify`

监听事件：

```text
created: podcasts/episode-002.txt
modified: podcasts/episode-001.summary.md
deleted: podcasts/episode-003.txt
```

然后增量更新数据库。

优点：

- 实时。
- 手动 CLI 生成文件后，主应用马上显示。

缺点：

- 监听可能漏事件。
- 网络盘、同步盘可能不稳定。

所以最好配合定期扫描。

---

## 3. CLI 主动通知主应用，可选

如果以后你希望更可靠，可以让 CLI 输出后写一个通知文件：

```text
.knowledge/inbox/
```

例如：

```text
.knowledge/inbox/artifact-20260816-103000.json
```

内容：

```json
{
  "schema": "kb.artifact.v1",
  "source_path": "podcasts/episode-001.mp3",
  "artifact_path": "podcasts/episode-001.txt",
  "kind": "transcript",
  "generator": "mytool-asr",
  "model": "whisper-large-v3",
  "created_at": "2026-08-16T10:30:00+08:00"
}
```

主应用监听 `inbox` 目录，发现后导入。

优点：

- 比纯文件命名更明确。
- 可以带模型、参数、时间、hash。
- 适合以后多个工具共用。

缺点：

- CLI 需要稍微改造。
- 初期不是必须。

---

# 九、推荐你采用“扫描 + 监听 + 命名规则”的组合

对于你当前状态，最实用的是：

```text
主应用启动时全量扫描
运行中文件监听
CLI 继续输出同目录同名 txt
主应用根据命名规则识别 artifact
```

先不要急着做复杂通知机制。

等你的 CLI 越来越多、参数越来越复杂，再考虑：

```text
CLI 写 manifest
主应用读 manifest
```

# 十、主应用数据库应该怎么设计？

建议用 SQLite。

最小表结构可以这样。

---

## assets 表

```sql
CREATE TABLE assets (
  asset_id TEXT PRIMARY KEY,
  title TEXT,
  type TEXT,
  relative_path TEXT UNIQUE,
  absolute_path TEXT,
  file_hash TEXT,
  size INTEGER,
  mtime INTEGER,
  created_at TEXT,
  updated_at TEXT
);
```

例如：

```text
asset_id = a1
title = episode-001
type = audio
relative_path = podcasts/episode-001.mp3
```

---

## artifacts 表

```sql
CREATE TABLE artifacts (
  artifact_id TEXT PRIMARY KEY,
  asset_id TEXT,
  kind TEXT,
  relative_path TEXT UNIQUE,
  file_hash TEXT,
  source TEXT,
  generator TEXT,
  model TEXT,
  mtime INTEGER,
  created_at TEXT,
  updated_at TEXT
);
```

例如：

```text
artifact_id = ar1
asset_id = a1
kind = transcript
relative_path = podcasts/episode-001.txt
source = cli
generator = mytool-asr
model = whisper-large-v3
```

---

## tasks 表

```sql
CREATE TABLE tasks (
  task_id TEXT PRIMARY KEY,
  asset_id TEXT,
  type TEXT,
  status TEXT,
  source TEXT,
  params_json TEXT,
  output_path TEXT,
  error TEXT,
  created_at TEXT,
  started_at TEXT,
  finished_at TEXT
);
```

例如：

```text
task_id = t1
asset_id = a1
type = transcription
status = success
source = app
output_path = podcasts/episode-001.txt
```

---

## notes 表，可选

如果你把笔记存数据库：

```sql
CREATE TABLE notes (
  note_id TEXT PRIMARY KEY,
  asset_id TEXT,
  content TEXT,
  created_at TEXT,
  updated_at TEXT
);
```

但我更建议初期把笔记存成 Markdown 文件：

```text
episode-001.notes.md
```

原因：

- 方便外部编辑器打开。
- 方便 Git 管理。
- 方便 Obsidian、VS Code、普通文本编辑器使用。
- 主应用数据库损坏也不丢笔记。

---

## chunks 表，用于全文和向量

```sql
CREATE TABLE chunks (
  chunk_id TEXT PRIMARY KEY,
  artifact_id TEXT,
  asset_id TEXT,
  chunk_index INTEGER,
  content TEXT,
  content_hash TEXT
);
```

向量索引可以单独用：

- sqlite-vec
- LanceDB
- Chroma
- Qdrant 本地模式
- DuckDB + vector 扩展

# 十一、搜索应该怎么实现？

你的需求是：

> 基于文件名、内容、向量搜索。

可以拆成三类。

---

## 1. 文件名搜索

直接查 assets 和 artifacts：

```sql
SELECT * FROM assets
WHERE title LIKE '%keyword%'
   OR relative_path LIKE '%keyword%';
```

例如搜索：

```text
episode
```

命中：

```text
podcasts/episode-001.mp3
```

---

## 2. 内容全文搜索

建议用 SQLite FTS5。

对以下内容建立全文索引：

```text
转录文本
文档解析文本
AI 总结
用户笔记
Markdown 文档
```

例如：

```sql
CREATE VIRTUAL TABLE chunks_fts USING fts5(
  content,
  content='chunks',
  content_rowid='rowid'
);
```

搜索：

```sql
SELECT * FROM chunks_fts
WHERE chunks_fts MATCH '知识管理';
```

优点：

- 本地。
- 简单。
- 对文本管理很够用。

---

## 3. 向量搜索

对 chunk 做 embedding：

```text
chunk -> embedding vector
```

存储：

```text
chunk_id
asset_id
artifact_id
vector
```

搜索时：

```text
用户 query -> query embedding
查询最相似的 chunks
返回对应 asset 和 artifact
```

适合：

```text
“那个讲本地知识管理架构的播客”
“关于 CLI 模块化的讨论”
“提到 sidecar 文件的文档”
```

---

# 十二、原始文件变化后如何处理？

这是一个很关键的问题。

例如：

```text
episode-001.mp3 被替换了
```

那么旧的转录文本可能已经失效。

建议主应用记录原始文件 hash：

```text
sha256
```

当扫描发现：

```text
path 没变，但 hash 变了
```

则：

```text
1. 更新 asset 记录
2. 标记相关 artifacts 为 stale
3. 提示用户重新转录 / 重新总结
4. 不自动删除旧结果，除非用户确认
```

例如：

```text
episode-001.mp3 hash changed
episode-001.txt marked stale
```

界面上可以显示：

```text
原始文件已变化，转录可能过期。
```

---

# 十三、派生文件变化后如何处理？

例如：

```text
episode-001.txt 被手动修改
```

主应用应该：

```text
1. 更新 artifact hash/mtime
2. 重新分块
3. 重建全文索引
4. 重建向量索引
```

如果是：

```text
episode-001.summary.md 被手动修改
```

同样重新索引。

但如果是 AI 重新生成总结，要注意：

> 不要覆盖用户手动改过的总结，除非用户明确选择覆盖。

---

# 十四、AI 总结和用户笔记要严格区分

你提到：

> 自动生成总结和笔记。

这里建议不要把它们混成一个东西。

---

## AI 总结

```text
episode-001.summary.md
```

特点：

- 可重新生成。
- 可多版本。
- 可以被覆盖或生成新版本。
- 内容来自原始文件或转录文本。

示例：

```markdown
---
type: summary
source: podcasts/episode-001.mp3
source_hash: sha256:xxxx
generator: mytool-summarize
model: qwen-local
created_at: 2026-08-16T10:40:00+08:00
---

# Episode 001 总结

本集主要讨论了本地知识管理系统的架构设计……
```

---

## 用户笔记

```text
episode-001.notes.md
```

特点：

- 用户手写。
- 不能被 AI 自动覆盖。
- 可以增量追加。
- 可以参与搜索。

示例：

```markdown
# 我的笔记

- 这个 episode 里提到的 sidecar 思路值得借鉴。
- 转录 CLI 后续需要支持输出 JSON segments。
```

---

## 如果 AI 要生成“笔记草稿”

不要直接写：

```text
episode-001.notes.md
```

可以写：

```text
episode-001.notes.draft.md
```

或者：

```text
episode-001.ai-notes.md
```

这样不会污染用户笔记。

推荐命名：

```text
{stem}.summary.md      AI 总结
{stem}.ai-notes.md     AI 生成笔记草稿
{stem}.notes.md        用户笔记
```

# 十五、主应用触发 CLI 时，建议增加任务记录

虽然 CLI 可以无状态，但主应用最好有状态。

也就是说：

```text
CLI 无状态没问题。
主应用必须有任务状态。
```

主应用点击“转录”时：

```text
创建任务
```

任务状态：

```text
pending
running
success
failed
cancelled
```

例如：

```json
{
  "task_id": "task_20260816_001",
  "asset_id": "asset_001",
  "type": "transcription",
  "status": "running",
  "command": [
    "mytool",
    "transcribe",
    "podcasts/episode-001.mp3"
  ],
  "expected_output": "podcasts/episode-001.txt",
  "created_at": "2026-08-16T10:20:00+08:00"
}
```

CLI 完成后，主应用检查：

```text
expected_output 是否存在？
文件是否非空？
hash 是否变化？
```

然后更新任务。

这样即使 CLI 很简单，主应用也能有完整体验。

# 十六、主应用调用现有转录 CLI 的具体方式

输出：


主应用可以这样调用：

```python
import subprocess

def run_transcribe(file_path):

        "mytool",
        "transcribe",

```

然后主应用检查同目录同名 txt：

```python
from pathlib import Path

def expected_transcript_path(audio_path: Path) -> Path:
    return audio_path.with_suffix(".txt")
```

例如：

```text
podcasts/episode-001.mp3
```

对应：

```text
podcasts/episode-001.txt
```

主应用发现该文件后：

```text
导入为 transcript artifact
```

# 十七、建议你的 CLI 后续增加 `--output`

虽然现在同名 txt 很方便，但长期建议你给 CLI 加几个参数：

```bash
mytool transcribe input.mp3 --output output.txt
mytool transcribe input.mp3 --output-json output.json
mytool transcribe input.mp3 --force
mytool transcribe input.mp3 --model large-v3
```

原因：

1. 主应用可以指定输出路径。
2. 可以避免覆盖已有文件。
3. 可以保留多版本。
4. 可以输出结构化 segments。
5. 便于未来 sidecar 目录。

例如未来可以：

```bash
mytool transcribe episode-001.mp3 \
  --output episode-001.kb/transcript.txt \
  --json episode-001.kb/transcript.json \
  --meta episode-001.kb/transcript.meta.json
```

但你不必一开始就改。

# 十九、主应用如何识别一个文件是原始文件还是派生文件？

你需要一个规则引擎。

例如：

```python
def classify_file(path):
    name = path.name

    if name.endswith(".summary.md"):
        return "artifact", "summary"

    if name.endswith(".notes.md"):
        return "artifact", "note"

    if name.endswith(".transcript.txt"):
        return "artifact", "transcript"

    if name.endswith(".transcript.json"):
        return "artifact", "transcript_meta"

    if path.suffix in AUDIO_EXTENSIONS or path.suffix in VIDEO_EXTENSIONS:
        return "asset", "media"

    if path.suffix in DOCUMENT_EXTENSIONS:
        return "asset", "document"

    if path.suffix == ".txt":
        # 需要进一步判断是否存在同名音视频
        return "maybe_transcript"

    return "unknown"
```

对于 `episode-001.txt`：

```text
检查同目录是否存在 episode-001.mp3 / m4a / wav / mp4 等
如果存在，则认为是 transcript
如果不存在，可以作为普通文档资产
```

例如：

```text
发现 podcasts/episode-001.txt
寻找同目录同 stem 的原始文件：
  episode-001.mp3 ✅
因此归类为 transcript artifact
```

如果找不到原始文件，可以有几种策略：

1. 当作普通文本文档管理。
2. 标记为“孤立派生文件”。
3. 不索引，等待用户处理。

我建议：

> 找不到原始文件时，先作为普通文档资产，同时标记 `orphan_artifact_candidate`。

# 二十二、自动生成总结和笔记的流程

以播客为例。

---

## 完整流程

```text
1. 导入 episode-001.mp3
2. 主应用创建 Asset
3. 检查是否存在 episode-001.txt
```

```text

```

或者：

```text

  自动解析
  自动生成摘要
  不自动向量化，等空闲时执行
```

注意任务优先级：

```text
用户主动操作 > 后台自动任务
```

# 二十三、任务、文件、索引三者如何同步？

建议你采用这个逻辑：

```text
文件变化
  -> 更新 Asset/Artifact 记录
  -> 更新索引
  -> 更新相关任务状态
```

而不是：

```text
任务完成
  -> 直接写数据库
  -> 不管文件是否真的存在
```

因为你有手动 CLI 场景，所以必须以文件为准。

---

## 同步器伪代码

```python
def sync_library(root):
    disk_files = scan_files(root)
    db_files = load_db_files()

    added = disk_files - db_files
    modified = find_modified(disk_files, db_files)
    deleted = db_files - disk_files

    for path in added:
        import_new_file(path)

    for path in modified:
        update_file(path)

    for path in deleted:
        mark_deleted(path)
```

---

## 导入新文件

```python
def import_new_file(path):
    if is_asset(path):
        asset = upsert_asset(path)

    elif is_artifact(path):
        asset = find_related_asset(path)
        if asset:
            upsert_artifact(path, asset)
            index_artifact(path)
        else:
            mark_orphan(path)
```

# 二十四、如何处理重复生成？

如果文件存在且原始文件 hash 没变：

适合节省资源。

适合你当前 CLI。

然后更新 latest：

```text
episode-001.transcript.txt
```

这个更稳，但需要 CLI 支持。

## 我的建议

当前阶段：

```text

```

后续：

```text
支持版本目录。
```

# 三十一、最终推荐方案

你的应用可以采用下面这个模型：

```text
知识库目录
├── 原始文件：音频、视频、文档
├── 派生文件：转录、总结、笔记、解析结果
└── .knowledge/
    ├── SQLite 数据库
    ├── 全文索引
    ├── 向量索引
    ├── 任务记录
    └── 配置
```

工作原则：

```text
1. 原始文件自由存放。
2. CLI 可以独立生成派生文件。
3. 主应用可以调用 CLI 生成派生文件。
4. 主应用通过扫描和监听发现所有文件。
5. 主应用根据命名规则关联原始文件和派生文件。
6. 数据库只是索引缓存，可随时重建。
7. AI 生成内容和用户笔记分开。
8. 搜索基于文件名、全文、向量三层。
```

一句话总结：

> **可以做，而且应该支持。最佳方式是把主应用做成“本地知识库索引和管理中心”，把 CLI 做成“无状态能力工具”。两者通过文件系统和命名约定连接，主应用既能触发 CLI，也能自动识别手动 CLI 生成的结果。**

user：
主应用我需要有个界面以便于查看，我使用python技术栈，应该做成gui还是electron

qwen：
如果你的主应用是 **Python 技术栈**，而且核心目标是：

- 查看和管理播客、视频、文档；
- 做文件名、全文、向量搜索；
- 查看转录、总结、笔记；
- 触发转录、总结等任务；
- 主要自用，不追求商业级跨平台桌面发行；

我的建议是：

> **不要首选 Electron。**
>
> 更推荐：**Python 后端 FastAPI + 本地 Web UI**。
>
> 如果你特别想要原生桌面窗口，再考虑 **PySide6** 或 **Tauri 包一层 Web UI**。

# 二、为什么不太推荐 Electron？

Electron 当然能做，而且很多知识管理应用都用 Electron，比如 Obsidian、Notion 桌面端、Logseq 等。

但对你的场景来说，Electron 有几个问题。

---

## 1. 你是 Python 技术栈，Electron 会引入第二套技术栈

Electron 本质上是：

```text
Node.js + Chromium + 前端
```

如果你用 Electron，通常会变成：

```text
Electron 前端
  ↓
调用本地 Python 服务 / Python CLI
```

也就是：

```text
TypeScript / JavaScript
+
Python
```

你会同时维护：

```text
Electron 主进程
渲染进程
前端框架
打包配置
Python 后端
Python CLI
两者通信
```

对自用工具来说，这个复杂度有点高。

---

## 2. Electron 体积和内存开销比较大

Electron 应用通常包含一个 Chromium。

即使只是一个小工具，打包后也可能：

```text
100MB 起步
```

运行时内存也比较高。

如果你只是本地自用，这不一定值得。

---

## 3. 你的核心能力已经在 Python 里了

你的转录、文档解析、TTS、向量、搜索，大概率都会用 Python：

```text
FastAPI
SQLite
Whisper
PyTorch / ONNX
llama.cpp / transformers
embedding 模型
LangChain / LlamaIndex
```

如果主应用再用 Electron，相当于：

```text
界面在 Node/JS
逻辑在 Python
```

通信成本会增加。

---

## 4. Electron 的优势你未必强烈需要

Electron 强在：

```text
复杂桌面交互
丰富前端生态
跨平台一致 UI
系统托盘
全局快捷键
自动更新
```

如果你只是自用：

```text
浏览器打开 localhost
```

其实已经足够。

---

# 十三、任务调用 CLI 示例

主应用触发转录时：

```python
import asyncio
from pathlib import Path

async def run_transcribe(file_path: Path):
    process = await asyncio.create_subprocess_exec(
        "mytool",
        "transcribe",
        str(file_path),
        stdout=asyncio.subprocess.PIPE,
        stderr=asyncio.subprocess.PIPE
    )

    stdout, stderr = await process.communicate()

    if process.returncode == 0:
        return True
    else:
        return False
```

FastAPI 里可以创建后台任务：

```python
from fastapi import BackgroundTasks

@app.post("/api/assets/{asset_id}/transcribe")
def transcribe_asset(asset_id: str, background_tasks: BackgroundTasks):
    background_tasks.add_task(run_transcribe_task, asset_id)
    return {"status": "accepted"}
```

# 十八、方案对比表

| 方案 | 适合程度 | 优点 | 缺点 |
|---|---:|---|---|
| FastAPI + 浏览器 Web UI | 非常推荐 | Python 友好，开发效率高，界面现代，容易扩展 | 默认不是桌面窗口 |
| NiceGUI | 推荐快速原型 | Python 写 UI，速度快，适合自用 | 复杂定制不如前端框架 |
| Streamlit | 适合原型 | 极快 | 不适合复杂文件管理 |
| Gradio | 适合单功能 Demo | 适合模型演示 | 不适合知识管理主界面 |
| PySide6 | 可选 | 原生桌面，文件管理强 | UI 现代感和 Markdown 生态不如 Web |
| Tkinter | 不推荐 | 简单 | 界面弱，不适合复杂应用 |
| Tauri + Python 后端 | 后期可选 | 比 Electron 轻，桌面体验好 | 构建链复杂 |
| pywebview | 可选 | 轻桌面化，Python 友好 | 依赖系统 WebView |
| Electron | 不推荐首选 | 生态强，桌面能力完整 | 重，双技术栈，Python 场景复杂 |

# 十九、最终建议

你的情况我建议这样选：

```text
如果你现在想快速看到效果：
    用 NiceGUI 或 FastAPI + HTMX

如果你想长期做成一个舒服的知识管理应用：
    用 FastAPI + React/Vue/Svelte

    用 PySide6

如果你非常熟悉前端，而且以后可能发布桌面应用：
    可以用 Electron，但不是首选
```

最推荐路线：

```text
第一阶段：

做出能扫描、能搜索、能查看、能调用 CLI 的版本
```

# 本地知识管理应用 PRD v0.1

## 1. 产品概述

### 1.1 产品名称

暂定：

```text
Local Knowledge Hub
```

中文名暂定：

```text
本地知识管理中心
```

---

### 1.2 产品定位

一个面向个人用户的本地知识管理应用，用于统一管理：

```text
播客音频
视频文件
各类文档
```

并围绕这些文件提供：

```text
查看
管理
转录
AI 总结
笔记
全文搜索
向量语义搜索
```

应用以本地文件系统为真实数据源，不强制改变用户原有目录结构。

---

### 1.3 核心目标

第一阶段要实现：

1. 用户可以新建或打开一个本地目录作为知识库。
2. 应用在该目录下创建隐藏目录 `.knowledge/` 存储应用数据。
3. 应用可以扫描并管理音频、视频、文档。
4. 应用可以识别已有 CLI 生成的派生文件，例如转录文本。
5. 应用可以触发已有转录 CLI。
6. 应用支持手动 CLI 生成的文件自动进入管理索引。
7. 应用支持文件名搜索。
8. 应用支持全文内容搜索。
9. 应用支持基于 LanceDB 的向量语义搜索。
10. 应用支持查看和编辑笔记。
11. 应用支持 AI 总结文件的查看、生成和索引。

---

### 1.4 第一阶段不做的事情

以下功能不在第一阶段范围内，或仅做最低支持：

```text
多用户系统
登录认证
云端同步
移动端
团队协作
双链知识图谱
复杂标签体系
版本历史管理
TTS 播放学习
字幕级音频跳转
自动备份
插件系统
复杂权限管理
```

一个本地目录作为知识库根目录。


知识库中的原始文件。

例如：


Asset 是知识管理的基本对象。

```text

向量搜索：LanceDB
```

# 7. 非功能需求

## NFR-01 本地优先

应用默认只在本机运行。

服务只监听：

```text
127.0.0.1
```

不暴露到局域网。

---

## NFR-02 隐私

默认不上传用户文件。

如果用户配置了远程 LLM 或远程 embedding API，需要明确提示。

---

## NFR-03 可重建性

删除：

```text
.knowledge/db.sqlite
.knowledge/vector/
```

后，应用应能通过重新扫描恢复：

```text
Asset
Artifact
全文索引
向量索引
```

但任务历史可以丢失。

用户手写笔记因为保存在文件中，不应丢失。

---

## NFR-04 性能目标

以下为初步目标，需根据实际文件规模调整。

### 扫描

```text
1,000 个文件：全量扫描 < 5 秒
10,000 个文件：全量扫描 < 30 秒
增量扫描：通常 < 2 秒
```

### 搜索

```text
文件名搜索 < 0.5 秒
全文搜索 < 1 秒
向量搜索 < 2 秒，5 万 chunk 内
```

### UI

```text
列表页打开 < 1 秒
详情页打开 < 1 秒，不含大文件渲染
```

转录和总结性能取决于 CLI 和模型。

---

## NFR-05 稳定性

要求：

```text
CLI 失败不影响 UI
文件监听事件需要防抖
大文件不能一次性读入内存做索引
SQLite 写入需要事务
长时间任务需要日志
```

---

## NFR-06 可维护性

代码结构要区分：

```text
UI 层
服务层
数据层
工具调用层
```

NiceGUI 页面不直接操作数据库和 CLI，应通过 service 调用。

# 9. 数据模型设计

## 9.1 assets 表

```sql
CREATE TABLE assets (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  type TEXT NOT NULL,
  relative_path TEXT NOT NULL UNIQUE,
  absolute_path TEXT NOT NULL,
  mime_type TEXT,
  size INTEGER,
  mtime INTEGER,
  file_hash TEXT,
  duration_seconds REAL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

字段说明：

```text
type: audio / video / document
relative_path: 相对知识库根目录路径
file_hash: 可选，默认可为空
duration_seconds: 可选，后续可从媒体元数据读取
```

---

## 9.2 artifacts 表

```sql
CREATE TABLE artifacts (
  id TEXT PRIMARY KEY,
  asset_id TEXT NOT NULL,
  kind TEXT NOT NULL,
  relative_path TEXT NOT NULL UNIQUE,
  absolute_path TEXT NOT NULL,
  file_hash TEXT,
  mtime INTEGER,
  source TEXT,
  generator TEXT,
  model TEXT,
  status TEXT DEFAULT 'active',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

字段说明：

```text
kind: transcript / transcript_meta / summary / note / parsed / meta
source: app / cli / external
status: active / stale / ambiguous / orphan
```

---

## 9.3 tasks 表

```sql
CREATE TABLE tasks (
  id TEXT PRIMARY KEY,
  asset_id TEXT,
  type TEXT NOT NULL,
  status TEXT NOT NULL,
  command TEXT,
  params_json TEXT,
  output_path TEXT,
  error TEXT,
  pid INTEGER,
  created_at TEXT NOT NULL,
  started_at TEXT,
  finished_at TEXT
);
```

字段说明：

```text
type: transcription / summarization / parsing / rebuild_fts / rebuild_vector
status: pending / running / success / failed / cancelled
```

---

## 9.4 chunks 表，用于全文搜索

```sql
CREATE TABLE chunks (
  id TEXT PRIMARY KEY,
  asset_id TEXT NOT NULL,
  artifact_id TEXT,
  kind TEXT NOT NULL,
  relative_path TEXT NOT NULL,
  chunk_index INTEGER NOT NULL,
  content TEXT NOT NULL,
  content_hash TEXT,
  created_at TEXT NOT NULL
);
```

为 FTS5 提供内容。

## 9.5 FTS5 表

```sql
CREATE VIRTUAL TABLE chunks_fts USING fts5(
```

# 11. 文件识别规则

## 11.1 原始文件识别

```text

```

---

## 11.2 派生文件识别

```text
{stem}.txt                  如果存在同 stem 音视频，则为 transcript
{stem}.transcript.txt       transcript
{stem}.transcript.json      transcript_meta
{stem}.summary.md           summary
{stem}.notes.md             note
{stem}.parsed.md            parsed
{stem}.meta.json            meta
```

---

## 11.3 歧义处理

如果：

```text
episode-001.mp3
episode-001.mp4
episode-001.txt
```

同时存在，则：

```text
episode-001.txt 不自动绑定
标记为 ambiguous
在 UI 中提示
```

后续可通过：


# 12. 核心流程

## 12.1 首次打开知识库

```text
1. 用户选择目录
2. 检查 .knowledge 是否存在
3. 不存在则创建
4. 初始化 config.toml
5. 初始化 SQLite
6. 初始化 LanceDB
7. 全量扫描
8. 建立 Asset / Artifact
9. 建立全文索引
10. 建立向量索引
```

---

## 12.2 主应用触发转录

```text
1. 用户点击生成转录
2. 创建 Task(status=pending)
3. 检查是否已有转录文件
4. 若无冲突，启动 CLI
5. Task(status=running)
6. 等待 CLI 结束
7. 检查输出文件
8. 写入 Artifact
9. 更新全文索引
10. 更新向量索引
11. Task(status=success)
```

---

## 12.3 手动 CLI 生成转录

```text
1. 用户终端运行 CLI
2. CLI 生成 txt
3. watchdog 发现新文件
4. 进入同步队列
5. 识别为 transcript artifact
6. 关联 asset
7. 更新数据库
8. 更新全文索引
9. 更新向量索引
10. UI 刷新状态
```

---

## 12.4 生成总结

```text
1. 用户点击生成总结
2. 创建 Task
3. 读取输入内容：
   - 音视频读取 transcript
   - 文档读取 parsed 或原文
4. 调用总结 CLI / LLM
5. 输出 summary.md
6. 识别为 summary artifact
7. 建立索引
8. Task 成功
```

---

## 12.5 搜索

```text
1. 用户输入关键词
2. 判断搜索模式
3. 文件名搜索：查询 assets/artifacts
4. 全文搜索：查询 FTS5
5. 向量搜索：
   - query embedding
   - LanceDB search
   - 返回 chunks
6. 根据 chunk 关联 asset/artifact
7. 展示结果
```

# 17. 风险与注意事项

## 17.1 同名派生文件歧义

风险：

```text
episode.mp3 和 episode.mp4 同时存在
episode.txt 无法确定属于谁
```

解决：

```text
标记歧义
后续支持 sidecar 目录
CLI 支持指定输出路径
```

---

## 17.2 大文件索引性能

风险：

```text
大型转录文本或文档导致分块和 embedding 慢
```

解决：

```text
异步任务
分块缓存
按 artifact hash 增量更新
限制单文件大小
```

---

## 17.3 Embedding 模型变化

风险：

```text
更换模型后向量维度不同，旧向量不可用
```

解决：

```text
记录 embedding_model 和 dimension
模型变化时提示重建 LanceDB
```

---

## 17.4 CLI 不稳定

风险：

```text
CLI 失败、卡住、输出异常
```

解决：

```text
任务超时
错误日志
重试机制
输出文件校验
```

---

## 17.5 用户编辑文件被覆盖

风险：

```text
AI 总结覆盖用户修改过的内容
```

解决：

```text
覆盖前提示
自动备份
用户笔记永不自动覆盖
```

# 本地知识管理应用 PRD v1.0

## 1. 产品名称与定位

### 1.1 产品名称

暂定：

```text
Local Knowledge Hub
```

中文名暂定：

```text
本地知识管理中心
```

---

### 1.2 产品定位

一个面向个人用户的本地知识管理应用，用于管理：

```text
播客音频
视频文件
文档文件
```

并围绕这些内容提供：

```text
统一查看
文件管理状态展示
转录任务触发
AI 总结生成
笔记文件管理
文件名搜索
全文搜索
向量语义搜索
```

系统以本地文件系统为真实数据源，不改变用户原有文件组织方式。

---

### 1.3 核心原则

```text
1. 本地文件优先，应用不移动、不重命名、不删除用户原始文件。
2. 派生文件落盘可见，可被外部 CLI 或手动编辑产生。
3. 应用数据库只是索引和缓存，可重建。
4. CLI 能力可独立使用，不依赖主应用。
5. 主应用负责查看、管理、任务调度和搜索。
6. 第一阶段只服务个人本地使用，不做多用户和云端能力。
```

---

## 2. 第一阶段目标

第一阶段要实现一个可自用的本地知识管理 MVP：

```text
1. 打开或新建本地知识库目录。
2. 在库目录下创建 .knowledge/ 应用数据目录。
3. 扫描音频、视频、文档文件。
4. 展示资产列表和详情页。
5. 识别已有转录 txt 文件。
6. 支持手动触发转录 CLI。
7. 支持手动刷新后识别外部 CLI 生成的文件。
8. 支持 AI 总结生成，调用 OpenAI 兼容 API。
9. 支持文件名搜索。
10. 支持全文搜索。
11. 支持基于 LanceDB 的向量语义搜索。
12. 支持笔记文件识别、只读预览和外部编辑器打开。
13. 支持配置 API、CLI、扫描规则和索引重建。
```

---

## 9. 派生文件规则

### 9.1 当前阶段规则

采用同目录同名 sidecar 文件。

原始文件：

```text
episode-001.mp3
```

可识别派生文件：

```text
episode-001.txt                  转录文本，兼容现有 CLI
episode-001.transcript.txt       转录文本，可选更明确命名
episode-001.summary.md           AI 总结
episode-001.notes.md             用户笔记
episode-001.parsed.md            文档解析结果，后续使用
episode-001.meta.json            元数据，后续使用
```

---

### 9.2 识别优先级

转录文本识别顺序：

```text
1. {stem}.transcript.txt
2. {stem}.txt
```

如果同时存在，优先：

```text
{stem}.transcript.txt
```

但第一阶段也可以两个都识别为 transcript artifact，并在 UI 中提示存在多个转录文件。

---

### 9.3 歧义处理

如果同目录存在：

```text
episode-001.mp3
episode-001.mp4
episode-001.txt
```

则 `episode-001.txt` 无法明确属于哪个 Asset。

第一阶段处理：

```text
标记为 ambiguous artifact
不自动绑定
在 UI 中提示
```

后续可通过：

```text
sidecar 目录
CLI 指定输出路径
更明确命名
```

解决。

---

### 9.4 后续 sidecar 目录预留

后续阶段支持：

```text
episode-001.mp3.kb\
├── transcript.txt
├── summary.md
```

第一阶段不要求实现，但数据模型要能兼容。

## 13. AI 总结功能

### 13.1 总结方式

根据你的选择，第一阶段没有总结 CLI。

因此总结由主应用直接调用：

```text
OpenAI 兼容 API
```

---

### 13.2 总结输入

优先级：P0

不同 Asset 的总结输入不同。

#### 音频/视频

必须存在转录文本：

```text
{stem}.txt
或
{stem}.transcript.txt
```

如果没有转录：

```text
禁用生成总结按钮
提示先生成转录
```

#### 文档

第一阶段可总结：

```text
.md
.txt
.html / .htm，若实现文本提取
```

暂不可总结：

```text
.pdf
.docx
.doc
.epub
```

原因是文档解析模块尚未实现。

后续文档解析 CLI 接入后，总结输入改为：

```text
{stem}.parsed.md
```

---

### 13.3 总结输出

输出文件：

```text
{stem}.summary.md
```

例如：

```text
episode-001.summary.md
```

文件内容建议包含 frontmatter：

```markdown
---
type: summary
source: episode-001.mp3
source_hash: 
generator: openai_compatible
model: gpt-4o-mini
created_at: 2026-08-16T12:00:00+08:00
---

# episode-001 总结

## 核心内容

...

## 关键点

...

## 可能值得后续关注

...
```

第一阶段即使模型输出没有 frontmatter，应用也应自动补充基础 frontmatter。

---

### 13.4 总结覆盖策略

优先级：P0

如果已有：

```text
episode-001.summary.md
```

重新生成时：

```text
提示已存在总结
用户确认后才覆盖
覆盖前备份到 .knowledge/backups/
```

备份命名建议：

```text
episode-001.summary.20260816-120000.md
```

---

### 13.5 长文本总结策略

优先级：P0

播客和视频时长大多在：

```text
30 分钟 - 2 小时
```

转录文本可能超过模型上下文限制。

第一阶段采用简单分层总结：

```text
1. 将转录文本按段落切块
2. 对每个块生成局部摘要
3. 将局部摘要合并生成最终总结
```

如果 API 调用失败，可降级为：

```text
截取前 N 个字符生成总结
```

并在总结 frontmatter 或任务日志中记录：

```text
summary_mode: truncated
```

---

### 13.6 总结 Prompt

配置中应支持 Prompt 模板。

默认模板示例：

```text
你是一个知识管理助手。
请根据下面内容生成中文总结。

要求：
1. 先给出 3-5 句核心总结。
2. 再列出 5-15 个关键点。
3. 如果内容包含行动项，请单独列出。
4. 不要编造不存在的信息。
5. 使用 Markdown 格式。

内容：
{content}
```

分段摘要模板示例：

```text
请总结下面这段内容，保留关键信息，输出简洁中文摘要。

内容：
{chunk}
```

合并摘要模板示例：

```text
下面是一篇长内容的多段摘要。
请根据这些摘要生成最终中文总结。

要求：
1. 先给出核心总结。
2. 再列出关键点。
3. 不要编造不存在的信息。

分段摘要：
{partial_summaries}
```

### 17.4 分块策略

第一阶段建议：

```text

```

切块顺序：

```text
优先按段落
段落过长按句子
句子过长按字符
```

### 17.5 Embedding API

使用 OpenAI 兼容 API。

配置项：

```toml
[embedding]
enabled = true
provider = "openai_compatible"
base_url = "https://api.example.com/v1"
api_key_env = "OPENAI_API_KEY"
model = "text-embedding-3-small"
dimension = 1536
batch_size = 32
timeout = 120
```

注意：

```text
dimension 必须和模型实际输出一致
模型或维度变化后需要重建向量索引
```

---

### 17.6 Embedding 缓存

为了减少 API 重复调用，需要缓存 embedding。

缓存数据库：

```text
.knowledge/cache/embeddings.sqlite
```

表结构：

```sql
CREATE TABLE embedding_cache (
  content_hash TEXT PRIMARY KEY,
  model TEXT NOT NULL,
  vector BLOB NOT NULL,
  dimension INTEGER NOT NULL,
  created_at TEXT NOT NULL
);
```

逻辑：

```text
1. 对 chunk 内容计算 content_hash
2. 查询缓存
3. 命中则直接使用
4. 未命中则调用 API
5. 写入缓存
```

如果模型变化：

```text
旧缓存不复用
```

---

### 17.7 向量更新

当 Artifact 变化：

```text
删除该 artifact_id 的旧向量
重新分块
重新 embedding
写入 LanceDB
```

当 Asset 删除：

```text
删除该 asset_id 的所有向量
```

---

### 17.8 向量重建

设置页提供：

```text
重建向量索引
```

重建时：

```text
清空 LanceDB chunks 表
重新扫描所有可索引 artifact
重新分块
重新 embedding
```

需要注意 API 成本。

## 30. 风险与应对

### 30.1 API 成本

风险：

```text
长播客总结和大库 embedding 会消耗 API token
```

应对：

```text
embedding cache
总结前提示
重建向量前提示预计规模
可关闭远程 API
```

---

### 30.2 长文本总结失败

风险：

```text
2 小时播客转录很长，API 可能失败
```

应对：

```text
分段摘要
合并摘要
失败降级截断
任务日志记录
```

---

### 30.3 Embedding 模型变化

风险：

```text
模型或维度变化导致旧向量不可用
```

应对：

```text
记录 embedding_model 和 dimension
检测维度不匹配
提示重建 LanceDB
```

---

### 30.4 同名文件歧义

风险：

```text
同 stem 多个媒体文件导致 txt 无法绑定
```

应对：

```text
标记 ambiguous
UI 提示
后续支持 sidecar 目录
```

---

### 30.5 Windows 路径和编码

风险：

```text
中文路径、空格路径、长路径、GBK 编码
```

应对：

```text
pathlib
subprocess argv
UTF-8 优先
错误日志记录具体路径
```

## 33. 仍需你后续提供的配置信息

开发时不需要立刻确定，但运行前需要配置：

```text
1. OpenAI 兼容 API base_url
2. LLM model 名称
3. Embedding model 名称
4. Embedding dimension
5. API Key 环境变量名
6. mytool 是否已加入 PATH
7. mytool transcribe --output 的实际参数格式
```

例如需要确认实际命令是：

```bash
mytool transcribe input.mp3 --output output.txt
```

还是：

```bash
mytool transcribe input.mp3 -o output.txt
```

```text
打包 exe
```
